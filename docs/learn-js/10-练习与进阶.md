# 10 · 练习题 + 下一步学什么

前面九章是「读」,这一章是「做」。题目全部指向这个项目里真实存在的文件,
做完你就等于把这个仓库摸了一遍。

做题的规矩:改完就 node test/core.test.mjs;跑完自己回答「我预期会怎样,实际怎样,
为什么不一样」—— 想清楚这三问,才算真做完。

--------------------------------------------
## 第一层:热身(熟悉工具和代码结构,8 题)

1. **跑起来**:克隆/进入仓库,跑全量测试。记下通过数。
   再故意把 test/core.test.mjs 里某个断言的条件取反,看输出长什么样,然后改回来。
2. **语法门**:挑一个 .mjs 文件,故意删掉一个大括号,跑 node --check,看报错行号准不准。
3. **模块地图**:把 agent-presets/roleplay/ 下所有文件列出来,
   每个写一句话说明它干什么(提示:文件头注释通常就写了)。
4. **纯函数改造**:在 lib/chat-core.mjs 的 historyMessages 里加一条规则:
   跳过文本长度小于 2 的消息。跑测试看哪几项受影响。
5. **日志定位**:在 lib/index.js 的 dispatch 里加一行 console.error 打印 endpoint,
   然后随便调一个 /roleplay 端点(用 PowerShell 的 Invoke-RestMethod),
   确认你的日志出现在 DSH 终端里。
6. **读配置**:打开 agent-presets/roleplay/agent.cordis.yml,数一数一共几行配置,
   说出每一行是干什么的(不知道的就查文档或问)。
7. **找常量**:在 roleplay-host.mjs 里找出「心跳间隔默认 30 分钟」这个值在哪儿,改成 15 试试。
8. **看懂一个 JSON**:打开 D:\dsh\.roleplay\character.json(只读!别改),
   说出里面每个字段大概是什么意思。

--------------------------------------------
## 第二层:动手改功能(9 题,都在安全范围内)

9. **加一个只读端点**:在 lib/index.js 的 KNOWN_ENDPOINTS 里加一个 'version',
   让它返回 { ok: true, value: { version: PKG_VERSION } },并在 dispatch 里实现。
   用 PowerShell 调通它。
10. **侧栏换个文案**:在 lib/client.js 里把「她正在想…」改成别的(顺便看看
    React 重渲染时它是怎么出现的)。
11. **限流**:给 chatSend 加一条「同一秒内只允许发一条」的限制(提示:用闭包里的时间戳),
    然后想一下:这个限制为什么放在引擎里,而不是浏览器里?
12. **加一个纯函数库**:新建 lib/my-core.mjs,写一个函数比如「把秒数格式化成 几分钟前」,
    然后在 roleplay-host.mjs 里 import 它并使用(注意 ?v=1 版本号,注意要加到测试的语法门列表里)。
13. **补一条测试**:为 12 题写的函数补 T 系列断言(照抄现有 T 的写法,数一数总数有没有 +1)。
14. **改进错误信息**:找一个「操作失败」这类笼统提示,改成带上具体原因
    (参考 lib/client.js 里 unwrap 的注释)。
15. **给一个工具加日志**:在 roleplay-host.mjs 的某个工具实现里加一行「谁在什么时候调用了它」,
    观察日志输出位置。
16. **配置文件技能**:在 agent-presets/roleplay/preset.yml 里改预设的显示名,
    重新物化(复制到 %USERPROFILE%\.dsh\.agent-presets\roleplay\),重启 DSH 看变化。
17. **写个临时诊断脚本**:tmp-inspect.mjs,读你的 .roleplay 目录,统计:
    有几个角色卡、最新一次日记是哪天、亲密度最高的角色是谁。

## 第三层:挑战(8 题,做完你对这个项目的理解就超过一般贡献者了)

18. **读懂一次完整调用链**:从浏览器点「发送」开始,把消息经过的每一层
    (client → HTTP → dispatch → 引擎 → agent 会话 → 模型 → 事件流 → 轮询回显)
    画成一张图,标上函数名。
19. **从会话日志取证**:自己写脚本解压 session.jsonl.zstd(zlib.zstdDecompressSync +++
    多帧解析),统计某个会话里「用户消息 / 助手消息 / 工具调用」各多少条。
20. **写一个门禁**:给测试加一条 T43:检查所有 .ps1 文件第一行不是空、且带 BOM
    (照 T0b 抄),并让它真的能抓出问题(临时改坏一个 ps1 验证)。
21. **模拟一次挂载失败**:把桌宠的导出改坏一处,重启 DSH 观察现象,
    再照着终端里的报错定位并修好。**这是最有价值的一题** ——它就是事故 B 的重演。
22. **浏览器侧实测**:用任意浏览器自动化工具(或手点也行)复现事故 C 的元素栈采样,
    证明「按钮被谁盖住了」。
23. **给自己写一个插件**:照 lib/index.js 的样子,写一个最小插件:
    挂一个 /hello 路由,返回 { ok: true, value: 'hi' },装进 DSH 并调通。
24. **性能优化**:给 pickMessages 写一个基准(生成 10 万条事件,比较改早停前后的耗时),
    并解释为什么 O(新增) 和 O(全量) 在长会话里差别巨大。
25. **写文档**:挑一个模块,给它写一份「五分钟能看懂」的说明(不超过 200 行),
    并让一个没读过这个项目的人照着它跑通一次。

## 怎么算「真的做完了」

每题都过一遍这三问:

- 我的预期是什么?
- 实际结果是什么?
- 不一样的地方,为什么?(不是「大概因为…」,而是能指到某一行代码)

如果第 3 问答不上来,别急着做下一题 —— 那才是你真正要学的东西。

--------------------------------------------
## 下一步该学什么(按优先级)

**1. TypeScript(最推荐先学)**
你会立刻喜欢上它:它把「运行时才发现类型错」提前到编辑器里。
学完之后回头看这个项目的 unwrap、typeof 判断,你会知道哪些是必要的、哪些是可以交给类型的。

**2. Node 深入**
事件循环的细节(宏任务/微任务)、流(stream)、worker_threads、
性能剖析(node --inspect)、诊断报告。

**3. 浏览器与前端**
DOM 事件模型(冒泡/捕获)、层叠上下文与 pointer-events、
现代 CSS(flex/grid/自定义属性)、浏览器 DevTools 的 Performance 面板。

**4. 测试与质量**
node:test 自带测试框架、断言库、覆盖率、
CI(GitHub Actions)跑门禁。

**5. 框架与架构**
Cordis 的官方文档(插件/服务/生命周期)、依赖注入的思想、事件驱动架构。
这个项目就是最好的练习场。

**6. 安全**
输入校验、路径穿越、权限最小化、沙箱、
「不要相信任何来自外部的数据」—— 项目里 readBody 的大小上限就是个例子。

**7. 工程习惯**
小步提交、写清提交信息、回归测试、编码规范(ESLint)、
以及最重要的一条:**改之前先想清楚「我怎么验证它没坏」**。

--------------------------------------------
## 资料清单(按有用程度排)

- MDN Web Docs —— 浏览器 API 和 JS 语言的首选参考,权威且例子多
- Node.js 官方文档 —— fs / path / child_process / zlib 这些都有示例
- javascript.info —— 教程性质,由浅入深,适合系统补课
- 《你不知道的 JavaScript》—— 讲作用域、闭包、原型这些「为什么」
- ECMAScript 规范(需要查精确语义时才看,平时不用)
- 本项目仓库本身 —— 最真实的教材;尤其是 docs/ 下的其他文档和 CHANGELOG
  (CHANGELOG 里每一条都是「现象 → 根因 → 修法」,是很好的案例库)

--------------------------------------------
## 最后一句

JS 最容易的地方是「写出来就能跑」,最难的地方也是这个 ——
没有编译器拦着你。所以真正拉开差距的不是语法熟练度,而是:

**证据意识(先看日志再改代码)、边界意识(每个入口都要兜住)、
验证意识(改完必须实测)。**

这三条,这个项目里的每一次事故都在重复教同一件事。祝玩得开心。
