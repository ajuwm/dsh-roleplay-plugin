# 06 · 插件与依赖注入:这套框架的世界观

前面几章是 JS 语言本身。这一章讲的是**这个项目跑在上面的框架**(DSH 用的 Cordis),
它决定了你写代码的形状:为什么到处是 ctx,为什么不是 import 而是 inject。

如果只挑一章理解这个项目,就是这一章。

--------------------------------------------
## 6.1 一切皆插件,一行行配置拼出一个程序

传统程序是你写 main() 自己 new 一堆对象。这套框架反过来:
**整个程序是一棵「插件树」,每个插件就是一行配置**。

看这个项目给平台写的配置(简化版,agent-presets/roleplay/agent.cordis.yml):

    - id: persona
      name: '@deepseek-ai/dsh-persona'
      config:
        text: 沉浸式角色扮演会话:完全以系统提示中的角色人设行事。

    - id: roleplay
      name: cordis:group
      group: true
      isolate:
        roleplay: true
      config:
        - id: roleplay-host
          name: './roleplay-host.mjs?gen=33'
          config:
            style: love

读法是:

- 每一项有个 id(这棵树里的门牌号)、name(要加载哪个模块)、config(它的配置);
- name 可以是包名('@deepseek-ai/dsh-persona')、相对路径('./roleplay-host.mjs?gen=33')、
  或者一个内建关键字('cordis:group' 表示这是个分组容器);
- group 里还可以再套一串子行。

好处:**功能是拼出来的**,不是写死的。同一份代码,恋爱向/朋友向/OC 向三套预设,
差别只是几个 config 字段(style: love / friend / oc)和各自的数据目录。

--------------------------------------------
## 6.2 ctx:插件的「万能把手」

每个插件长这样(roleplay-host.mjs):

    export const name = 'roleplay-host'
    export const inject = ['agents', 'fs', 'systemPrompt', 'timer', 'sandboxPolicy', 'tools', 'subprocess', 'attachments']
    export function apply(ctx, config) {
      const agents = ctx.agents          // 拿到「会话管理」服务
      const fs = ctx.fs                  // 拿到带沙箱的文件服务
      const REL_ROOT = config.dataRoot || '.roleplay'   // 拿到自己的配置
      ...
    }

三件事一次说清:

1. **name**:这个插件叫什么(日志、诊断里会看到);
2. **inject**:我依赖哪些服务 —— 这是个字符串数组,声明式;
3. **apply(ctx, config)**:框架准备好之后来调你,把 ctx(和你的配置)交给你。

【C++ 老习惯会坑你】这里不是 #include 也不是全局单例。
你**不能自己去 new 一个文件服务**,只能说「我要 fs」,由框架决定给你哪个实现。
好处是可替换、可 mock(测试里就是这么干的)、加载顺序自动化。

--------------------------------------------
## 6.3 依赖注入:为什么要绕这一圈

对比一下两种写法:

    // 传统:自己去找依赖
    import fs from 'node:fs'
    fs.writeFileSync('D:/somewhere/state.json', data)      // 硬编码路径,想换实现没法换

    // DI:声明依赖,由框架注入
    export const inject = ['fs']
    export function apply(ctx) {
      const fs = ctx.fs
      const target = await resolveFile('.roleplay/character.json')   // 走沙箱校验
      await fs.writeText(target, data, undefined, undefined, policyFor())
    }

DI 带来的实在好处:

- **顺序自动**:框架会等 fs 服务就绪再调你的 apply(不用担心谁先谁后);
- **可替换**:测试里塞个假 fs 就能跑(项目的 T35/T41 测试就是这么做的);
- **可拦截**:沙箱、日志、限流都挂在服务实现上,插件改不了也绕不过;
- **可卸载**:插件被移除时,它注册的东西自动收回(见 6.5 的 effect)。

## 6.4 服务:provide / get / serviceFor

插件也可以**对外提供服务**。扮演引擎就把自己包成一个 roleplay 服务:

    ctx.provide('roleplay', {
      getState: async (args) => { ... },      // 给侧栏读状态
      peek:     async () => { ... },          // 轻量查询(不触发副作用)
      chatSend: async (args) => { ... },      // 发消息
      chatPoll: async (args) => { ... },      // 增量拉消息
      stop:     async (args) => { ... },
    })

三种「拿服务」的方式,别混淆:

- **inject + ctx.xxx**:插件自己声明要用的(推荐,框架管顺序);
- **ctx.get('名字')**:运行中临时取一个可选服务(取不到返回 undefined,不报错);
- **agentPresets.serviceFor(agent, '名字')**:按会话拿「那一个会话自己的」服务实例
  —— 项目里的桥接就用它,做到「同一个插件,每个会话状态互不干扰」。

有一处特别容易踩:如果服务被注册在**隔离域(isolate)里**,那么从外面 ctx.get 是看不见的。
项目里桌宠就中过这一枪:服务在隔离域里,桥接在外面读,永远读不到,
侧栏一直显示「未挂载」。后来把隔离域去掉就好了(见 6.6)。

--------------------------------------------
## 6.5 生命周期:apply 一次,effect 管收拾

插件的寿命:被挂载 → apply 执行 → 运行 → 被卸载。卸载时你得把占用的东西收回去:

    ctx.effect(() => webServer.register(route), 'roleplay-client: /roleplay raw prefix')

意思是「注册这条路由,顺便记下撤销它的办法」。插件卸载时,框架会调用返回的那个函数。

定时器、监听器、路由、各种注册,都应该这么写 ——
这也是为什么项目里那些桌面窗口和子进程要显式收尾(资源不会被 GC 顺手收掉)。

【本项目的血泪】清理钩子也有「能不能用」的问题。桌宠原来写的是:

    ctx.on('dispose', () => { stopPet(); stopNotes() })

在它当时的运行上下文里,这个 API 根本不成立,结果 apply 直接抛异常,
整个插件行加载失败 —— 也就是 6.6 里那类「一行挂,全树挂」的事故。
最后改成框架原生支持的写法,问题才消失。教训:**清理也要按框架的规矩来,别凭感觉写。**

## 6.6 事件与 waterfall:一个钩子写错,整轮对话都完蛋

插件可以在关键节点插一脚。这个项目最重要的一脚插在 agent 的「即将开始这一轮」:

    ctx.on('agent/pre-step', async ({ agent, messages: claimedMessages, turn, step, signal }, next) => {
      let decision = null
      try {
        if (!selfAgent && agent) selfAgent = agent
        await ensureLoaded()
        decision = await next()                       // 先把链交给下一个钩子
        if (decision === undefined || decision === null) {
          const keep = Array.isArray(claimedMessages) ? claimedMessages : []
          return { kind: 'enter', messages: keep }    // 绝不给外面 undefined
        }
        if (decision.kind === 'reject' || (signal && signal.aborted)) return decision
        const messages = decision.messages || []
        ...
        return kept.length === messages.length ? decision : { kind: 'enter', messages: kept }
      } catch (e) {
        console.error('[roleplay] agent/pre-step failed:', e && e.stack ? e.stack : e)
        if (decision && typeof decision === 'object' && typeof decision.kind === 'string') return decision
        const keep = Array.isArray(claimedMessages) ? claimedMessages : []
        return { kind: 'enter', messages: keep }
      }
    }, { prepend: true })

这段代码里藏着三条硬规矩,条条都是用事故换来的:

1. **waterfall 的返回值就是「决定」**。它长的样子必须是 { kind: 'enter'|'reject', messages }。
   你给别的,外面一读 .kind 就崩 —— 报错就是那句
   「Cannot read properties of undefined (reading 'kind')」,用户看到的是「本轮运行失败」的红牌。
2. **前面的钩子要调 next()**,把链子往下传;不调就相当于「我把这件事拦下来了」。
3. **绝不返回 undefined**。我们曾经写过 catch 里 return undefined 「假装没事」,
   结果外面拿到 undefined,一取属性就炸 —— 报错信息跟真因完全不同,
   排查了半天。现在的做法是:出错也要返回一个**合法的空决定**,并且把真实堆栈打进控制台。

【C++ 老习惯会坑你】C++ 里异常可以一路往上抛,让顶层处理。
在这里,「往外抛」等于「把用户的这一轮对话搞挂」——
**边界的职责是兜住,不是转嫁**。这是插件开发里最容易违反的一条。

## 6.7 隔离域(isolate):服务也能有「私有命名空间」

配置里那个:

    isolate:
      roleplay: true

意思是:这个分组里的插件发布的 roleplay 服务,**只属于这一个预设实例**,
别的会话、别的预设都有自己的那一份,互不干扰。这是「一个插件要在 N 个会话里各跑一份」
的正确做法。

但要注意两个方向:

- 从**里面**往外看:能看见根上的公共服务(agents、fs 那些);
- 从**外面**往里看:看不见隔离域内的服务 ——
  除非走框架提供的「按会话解析」接口(本项目桥接用的 serviceFor 就是干这个的);
- 如果你把服务搬到了 host 平面(不再在隔离域里),那就走普通的 ctx.get。

**判断口诀**:会话级的东西放隔离域 + serviceFor 取;工作区级/全局的东西放根上 + ctx.get 取。
桌宠就是「工作区级」的(全工作区只有一个桌面窗口),所以它不该在隔离域里。

## 6.8 配置从哪来

apply 的第二个参数 config 就是 cordis.yml 里那一行下面的 config 字段,
原样(经过校验后)交给你:

    - id: roleplay-host
      name: './roleplay-host.mjs?gen=33'
      config:
        style: love
        dataRoot: .roleplay

对应的代码:

    const STYLE = (config && config.style) || 'love'
    const REL_ROOT = (config && config.dataRoot && typeof config.dataRoot === 'string')
      ? config.dataRoot : '.roleplay'

框架只会校验「结构」,不会保证「业务上合理」,所以默认值 + 类型判断还是要自己写。

--------------------------------------------
## 这一章记住三件事

1. 插件 = 一行配置 + 一个 apply(ctx, config);依赖靠 inject 声明,别自己去 new;
2. 发布服务用 provide;按会话拿服务用 serviceFor,全局服务用 ctx.get,
   隔离域会把服务藏起来;
3. waterfall 钩子的返回值就是决定:必须合法,绝不 undefined,出错也要兜住并记堆栈。
