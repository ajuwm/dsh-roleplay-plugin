# 09 · 实战复盘:三个真实 bug 是怎么破的

前面几章讲的是「怎么写」。这一章讲「怎么查」—— 用这个项目真实发生过的三起事故。
如果你只看一章,看这章,因为它教的是**遇到没见过的问题时,你该怎么下手**。

--------------------------------------------
## 事故 A:侧栏聊天全挂 —— 「本轮运行失败 Cannot read properties of undefined (reading 'kind')」

**现象**:在侧栏(💬)发消息,主对话区和侧栏都出现红色徽标「本轮运行失败」,
但同一个会话里点桌宠「摸头」却一切正常。

**一开始的猜测**(错的):以为是侧栏 UI 的渲染代码读了不存在的字段,
或者轮询游标算错了。改了两轮客户端代码,没用。

**转折点:去翻证据。** DSH 把每个会话的事件流存成压缩日志
(sessions/<会话>/session.jsonl.zstd)。我用 Node 自带的 zstd 解压,一条条看事件,
于是看到这样一组:

    {"type":"agent/inbox/spliced","seq":45613,"data":{"inserted":[{"id":"chat-mtpg2eqw-vn4rdg","role":"user","content":[{"type":"text","text":"hi"}]}]}}
    {"type":"turn/start","seq":45614}
    {"type":"agent/inbox/spliced","seq":45615,"data":{"removedCount":1,"inserted":[]}}
    {"type":"turn/end","seq":45616,"data":{"reason":{"kind":"error","error":{"message":"Cannot read properties of undefined (reading 'kind')"}}}}

再看同一天的桌宠消息(它是好的):

    {"type":"agent/inbox/spliced",...:[{"id":"pet-mtpg7izh-1","role":"user","content":[...],"source":{"kind":"plugin","plugin":"deskpet"}}]}

**两条消息一对比,差别只有一个字段:** 侧栏消息**没有 source**,桌宠消息有
source: { kind: 'plugin' }。

**根因**:DSH 内核在每一轮开始前的钩子链里,会读每条消息的 message.source.kind
(用来判断这条消息是用户打的、还是插件注入的)。没有 source,那句读取就抛
「Cannot read properties of undefined (reading 'kind')」—— 也就是用户看到的那句话。

**为什么「之前加过的防御」没解决问题?** 更值得学的一层:当时给插件自己的钩子加了
try/catch,catch 里写了 return undefined「假装没事」。可这个钩子的返回值就是
「这一轮的决定」,外面拿到 undefined 一读 .kind,**报的还是同一句话**。
防御把**真实原因**藏起来了,症状一点没变。

**修复**:
1. 侧栏发消息时补上 source: { kind: 'user' }(语义上它确实是用户发的);
2. 钩子改成「绝不返回 undefined」:出错就返回一个合法的空决定,并把真实堆栈打进控制台。

**教训**:
- 出了怪问题,**先去翻日志/事件流**,别急着改代码;
- 跨模块的数据结构(**契约**)要当接口看:少一个字段就能炸掉整条链;
- 「防御性代码」如果吞掉了原因,它就是在帮你隐藏 bug。

## 事故 B:恋爱向预设点不动 —— 选完自动跳回「标准模式」

**现象**:新会话里选「恋爱向」,几秒后自动跳回「标准」;
老的恋爱向会话也起不来,提示「当前会话没有挂载角色扮演插件」。

**第一步:复现。** 我在浏览器里把整套操作走了一遍(点新会话 → 打开模式菜单 → 点恋爱向),
确认了「静默跳回」这个行为,也顺便发现菜单里预设都在(说明清单没坏)。

**第二步:二分。** 预设加载不起来,那就猜「哪一行配置有问题」。
这个预设比朋友向预设多的东西里,最可疑的是**桌宠那一组配置**。
于是我把桌宠那段注释掉,重新加载 → 恋爱向**立刻能用了**。
范围锁定,不用再猜。

**第三步:找出为什么那一行会挂。** 这里花了最久,因为它是三层叠在一起的:

1. **模块系统**:桌宠文件是 CJS(module.exports/require),但包声明了 type: module →
   Node 按 ESM 解析 → 「module is not defined in ES module scope」→ 文件加载失败;
2. **失败会连坐**:DSH 认为这个组合里有一行不可用,**整棵预设挂载被回滚** ——
   于是恋爱向预设等于不存在(这就是「选完跳回标准」);
3. **搬位置之后又撞上两件事**:桌宠是「整机一个窗口」的东西,不该待在会话级预设里,
   我把它搬到宿主平面;结果又发现——它原来的服务被放在**隔离域**里(外面读不到),
   而且它用的几个 API(setInterval、ctx.on('dispose'))在当前运行环境里根本不成立。

**修复**:桌宠改名 deskpet.mjs(标准 ESM)、搬到宿主平面的配置里、去掉隔离域、
按当前环境真实支持的 API 重写那几处调用。

**教训**:
- **一行配置可以搞垮一整棵组合**:改插件组合时,先想清楚「这一行失败会怎样」;
- **二分法永远好用**:能注释就注释,能拆就拆,把范围砍到最小;
- 框架的 API **以你当前环境实际支持的为准**,别凭印象写(不同版本差别很大);
- 「这个东西属于哪个层级」这个判断很重要:会话级的放预设,整机级的放宿主。

## 事故 C:界面点不动、输入框浮到弹窗上 —— 全是「层」的问题

**现象**(连着来的三个怪事):
1. 点 🎭 按钮「没反应」,侧栏打不开;
2. 我修完之后,用户发现输入框浮到了「设置」弹窗的蒙层**之上**;
3. 用户还问:背景怎么多了一排排小圆点?

**破案工具:浏览器里数「层」。** 我打开页面,对按钮中心点做了一次
「元素栈采样」(浏览器 API:document.elementsFromPoint(x, y)),
结果一目了然:

    最上层: xx-bubble(宠物插件的说话气泡,z-index: 1199)
    下面:   宠物立绘图层(z-index: 60)
    最下面: 我们的 rp-dock-btn(按钮)

也就是说:**点击确实发生了,但它被上面的浮层吃掉了**,按钮压根没收到。

**第一个修法(错的)**:把输入区容器的 z-index 抬到 1300。
按钮是能点了 —— 但输入框也跑到「设置」弹窗(它的蒙层 z-index 是 1000)**上面**去了,
于是有了用户的第二条抱怨。

**为什么错**:z-index 的争夺是有底线的。
- 宠物的气泡是 1199,DSH 自己的弹窗是 1000 —— 也就是说,**「比气泡高、又比弹窗低」的
  z 值根本不存在**;
- 想压过气泡,就必然压过弹窗 —— 输入框浮到弹窗之上,是必然结果,不是运气问题。

**正确的修法**:不抢层,改**位置**。宠物固定在右下角约 200×200 的区域,
那就把我们的按钮往左挪出这个区域:

    body:has([data-dsh-whale-root]) .rp-dock { margin-right: 210px !important; }

问题消失,弹窗层级也恢复原样。

**第三个问题(圆点)的答案**:那不是 bug —— 是界面自己的背景纹理/宠物特效。
**分清「正常现象」和「故障」也是一项能力**:如果连正常渲染都要「修」,你会把系统越修越乱。

**教训**:
- 界面上「点了没反应」,先怀疑**被盖住**,而不是事件没绑上;
- 层叠上下文是有规则的:父子上下文、z-index、pointer-events,一个都不能想当然;
- **改 UI 一定要能"看到"**:要么在浏览器里实测(自动化也算),要么截图对比,别纯靠读代码猜;
- 修之前先问一句「这一层到底该谁在上面」,答案往往不是「我」。

## 一套可复用的排查流程(这三起事故共同验证过的)

1. **复现**:先让它稳定地坏一次。不能复现的问题,基本没法修。
2. **记录现象**:报错原文、截图、时间点、当时在干什么 —— 一字不差地抄下来。
3. **找证据**:日志、事件流、元素栈、堆栈、终端输出。**证据 > 直觉**。
4. **缩小范围**:二分法(注释、拆配置、换输入),把可疑面砍到最小。
5. **定位到「哪一行」**:能说出「就是这一行导致」为止,否则接着找。
6. **修,而且只修这一处**:顺手的「优化」留到下一次提交。
7. **验证**:重跑测试 + 真实环境实测(自己点一遍)。**没验证过的修复等于没修**。

其中第 3 步和第 7 步是新手最容易跳过的,而它们恰恰是这三起事故里最关键的两步。

--------------------------------------------
## 动手改一改

1. 把事故 A 的那两条事件(有 source 的 / 没 source 的)抄到一个 txt 里,
   自己写一段 JS:遍历事件、取出每条消息的 source.kind,
   故意不防空洞 —— 看它抛的是什么错。再补上防御,体会两者的区别。
2. 打开浏览器控制台,对任意一个按钮做一次元素栈采样:
   document.elementsFromPoint(x, y)(x、y 取按钮中心),看看它上面都压着谁。
3. 找一处你写的代码,按上面 7 步流程假想排查一遍:先写下「我会去哪儿找证据」。

--------------------------------------------
## 这一章记住三件事

1. 先复现、再看证据,最后才动手改;
2. 一个字段/一行配置/一个 z-index,都能构成完整的根因 —— 别嫌问题小;
3. 修完必须实测;防御代码绝不能吞掉真实原因。
