# 04 · 模块:ESM、CJS,和一场真实血案

模块这件事,在 C++ 里就是 #include + 头文件 + 链接。JS 的历史包袱更重:
有两套模块系统,互不兼容却经常混着用。这个项目正好两种都踩过,还因此挂过一次。

--------------------------------------------
## 4.1 为什么要模块

没有模块的年代,大家靠一堆 script 标签和全局变量。模块要解决三件事:
**作用域隔离**(各写各的,不污染全局)、**显式依赖**(用了谁一目了然)、
**可复用**(装成包给别人的项目用)。

JS 里现在有两种:

| | ESM(现代) | CJS(老,Node 自古有之) |
|---|---|---|
| 语法 | import / export | require() / module.exports |
| 文件 | .mjs,或 type 为 module 的 .js | .cjs,或没写 type 的 .js |
| 加载 | 静态解析依赖图 | 执行到那行才去要 |
| 顶层 await | 支持 | 不支持 |
| 现状 | 新代码都用它 | 老包还在用,基本当兼容层 |

--------------------------------------------
## 4.2 ESM 怎么写(项目里的样子)

导出(roleplay-host.mjs 头部):

    export const name = 'roleplay-host'
    export const inject = ['agents', 'fs', 'systemPrompt', 'timer', 'sandboxPolicy']
    export function apply(ctx, config) { ... }

    // 也可以默认导出
    export default { name: 'deskpet', inject: [...], apply(ctx, config) { ... } }

导入(同一个文件):

    import os from 'node:os'
    import path from 'node:path'
    import { applyDelta, reqCheck } from './lib/relation-core.mjs?v=16'
    import { pickMessages } from './lib/chat-core.mjs?v=2'

三个细节,每个都有讲究:

1. **内置模块写 node: 前缀**(node:fs、node:path)。不写也认,但写了更清楚,
   还能防止有人装个同名 npm 包把你劫持了。
2. **相对路径必须带扩展名**(./lib/chat-core.mjs)。ESM 不做猜测式解析,
   不写扩展名直接报错 —— 这点跟 C++ 的 #include 习惯很不一样。
3. **?v=16 这种查询串是「缓存版本号」**。DSH 会缓存预设模块,
   带个不同的版本号相当于给模块一个新身份,旧缓存自然失效。
   代价是:忘了改,你改的代码可能根本没生效(09 章还会遇到这个坑)。

## 4.3 CJS 怎么写(桌宠以前的样子)

    const os = require('node:os')
    const path = require('node:path')

    module.exports = {
      name: 'deskpet',
      inject: ['agents', 'subprocess', 'timer', 'fs', 'sandboxPolicy', 'webServer'],
      apply(ctx, config) { ... },
    }

一眼可见:CJS 用的是函数调用和对象赋值,不是语法关键字。
因此它没法被静态分析 —— 也就没有「提前知道依赖图」这回事。

--------------------------------------------
## 4.4 Node 怎么判断一个 .js 属于哪种模块

规则其实很短:

1. 后缀 .mjs → 一定是 ESM;
2. 后缀 .cjs → 一定是 CJS;
3. 后缀 .js → **看离它最近的 package.json 里有没有 "type": "module"**:
   有就是 ESM,没有就是 CJS(Node 的默认值)。

**「最近的那个 package.json」是关键**:同一个 .js 放在不同目录里,
可能被当成不同的模块系统。这个项目就栽在这上面。

--------------------------------------------
## 4.5 血案:一个 module.exports 把「恋爱向」预设干掉了

真事,2026-09-07。过程大概是这样:

**现象**:点「新会话 → 恋爱向」,几秒后自动跳回「标准模式」;
以前的恋爱向会话也打不开,提示「当前会话没有挂载角色扮演插件」。

**排查**:一行行试,最后用「把桌宠那段配置注释掉再启动」锁定了范围 ——
只要有桌宠这一行,恋爱向预设就挂不上。

**根因**:桌宠文件当时叫 deskpet.js,里面是 CJS:

    module.exports = { name: 'deskpet', ... }
    const os = require('node:os')

可它在插件包里,而插件的 package.json 写着 "type": "module"。
于是 Node 按 ESM 解析这个文件 → **module is not defined in ES module scope** → 加载失败 →
DSH 认为这个预设组合里有一行不可用 → **整棵预设挂载被回滚** → 恋爱向预设等于不存在。

终端里那句报错原文:

    Error: failed to import loader entry deskpet-host: module is not defined in ES module scope
    This file is being treated as an ES module because it has a '.js' file extension and
    '...\node_modules\@ajuwm\dsh-roleplay-plugin\package.json' contains "type": "module".

**修复**:改名 deskpet.mjs,并改成标准 ESM(export default + 顶层 import)。

【C++ 老习惯会坑你】C++ 里文件就是文件,内容决定一切。
JS 里**文件名、以及目录里的 package.json,都会影响「这个文件是什么」** ——
所以改文件名不是审美问题,是语义问题。

## 4.6 包的「出口」:exports 字段

一个 npm 包不想让人随便 import 内部文件,可以在 package.json 里声明出口:

    {
      "name": "@ajuwm/dsh-roleplay-plugin",
      "type": "module",
      "exports": {
        ".":              "./lib/index.js",       主入口
        "./client":       "./lib/client.js",      浏览器半边
        "./settings":     "./lib/settings.js",
        "./deskpet":      "./agent-presets/roleplay/deskpet.mjs",
        "./package.json": "./package.json"
      }
    }

有了 exports,外面只能按这几条路进来。好处有两个:
对内随便重构不怕破坏别人的 import;对外 import '@ajuwm/dsh-roleplay-plugin/deskpet' 时,
Node 会照这张表去找文件。

【C++ 老习惯会坑你】exports 是白名单:没列出来的路径一律进不去,哪怕文件真在那儿。
所以这个项目给桌宠单独开了一条 ./deskpet。

--------------------------------------------
## 4.7 混着用的现实规则

- ESM 里可以 import CJS:拿到的默认导出就是 module.exports;
- CJS 里不能直接 require ESM(老 Node 会报错,新 Node 支持一部分,别依赖);
- 同一个模块别既当 ESM 又当 CJS(双包问题,坑很深);
- 动态加载用 await import('./x.mjs'),它返回 Promise,适合按需加载。

项目里的动态 import 主要在两处:测试里按临时目录反复加载引擎(每次都想要全新实例),
以及临时玩模块时的 node -e "import(...)"。

--------------------------------------------
## 4.8 循环依赖:知道有这回事就行

模块互相 import 就可能成环。C++ 的头文件成环会编译不过;
JS 里可能「拿到一个还没填好的空对象」,表现为运行中莫名其妙的 undefined。

项目的规避办法很朴素:**只做单向依赖** —— 纯函数库(lib/*.mjs)不依赖引擎,
引擎依赖它们,谁也不反向依赖引擎。

## 这一章记住三件事

1. .mjs 一定是 ESM;.js 看最近那个 package.json 的 type —— 这条规则会咬人;
2. ESM 相对导入要写扩展名,内置模块用 node: 前缀;
3. 一个文件加载失败,可能连累整棵上层组合 —— 所以「一行都不能错」。
