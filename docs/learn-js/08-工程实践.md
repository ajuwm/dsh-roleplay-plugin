语法会用只是入门。这一章讲的是「把东西写对、写稳、写坏了还能查出来」的那套手艺 ——
这部分经验,比语法重要得多。

## 8.1 测试:这个项目没用任何框架,自己写了 200 行

打开 test/core.test.mjs,开头是这样的:

    import { spawnSync } from 'node:child_process'
    ...
    console.log('\nT0 语法门 (全部 JS/MJS)')

    let pass = 0, fail = 0
    const failures = []
    const ok = (cond, label) => {
      if (cond) { pass++; console.log('  ✅ ' + label) }
      else { fail++; failures.push(label); console.log('  ❌ ' + label) }
    }

就这么点东西。原理是:

- 每个「测试」就是一句 ok(条件, 说明);
- 失败就记下来,最后打印统计;
- 全绿就 exit 0,有失败就 exit 1(这样 CI 才能看明白)。

为什么不用 Jest/Vitest 那些?两个理由:

1. **零依赖**:这个插件是给别人的 DSH 装的,依赖越少越不容易坏;
2. **够用**:两百多项断言跑完不到几秒,而且失败信息是自己写的,看得懂。

【C++ 老习惯会坑你】JS 世界里「测试框架」是可选品,不是必需品。
node:test 是 Node 自带的,但一个 ok() 函数也能撑起一个项目 —— 关键是**门禁意识**,
不是框架牌子。

## 8.2 这个项目的测试分几层(照着这个思路设计你自己的)

| 层 | 名字 | 测什么 | 例子 |
|---|---|---|---|
| 门禁 | T0 | 每个 JS/MJS 文件语法能不能过 | node --check 全部文件 |
| 门禁 | T0b | PowerShell 脚本有没有 BOM、语法对不对 | 调 powershell 解析器 |
| 纯函数 | T1~T40 | 关系/时间/记忆/备份/便签这些逻辑 | 给输入,断言输出 |
| 集成 | T35/T36/T41 | 把引擎真的跑起来(mock 掉外部服务) | 起一个假 ctx,调用 chatSend |
| 契约 | T42 | 钩子在各种异常输入下的行为 | next() 返回 undefined 时必须兜住 |

最值得学的一招是**「假 ctx」**:集成测试不想启动整个 DSH,那就造一个最小的 ctx:

    const ctx = {
      get: () => undefined,
      on: (ev, h) => { (captured.events[ev] ||= []).push(h) },   // 把注册的钩子抓下来
      provide: (n, s) => { if (n === 'roleplay') captured.svc = s },
      tools: { register: (e) => { captured.tools[e.name] = e } },
      agents: { currentInitiator: () => fake, get: () => fake, roots: () => [fake] },
      fs: fsx,                       // 假的文件系统,读写都在临时目录
      timer: { interval: () => 0, setTimeout: () => 0 },
    }
    mod.apply(ctx, { style: 'love', dataRoot: '.roleplay' })

然后就能直接调 ctx 里抓到的那些服务方法了。**这就是依赖注入送你的礼物**:
只要接口对得上,真实现和假实现随便换。

## 8.3 调试:六个真正管用的手段

1. **node --check 文件** —— 比跑测试快,改完先看语法;
2. **console.log / console.error 打变量** —— 最土也最快,项目里到处是
   console.error('[deskpet] startPet dir=... script=...') 这种带前缀的日志,
   好处是 grep 一下就知道是谁打的;
3. **读堆栈** —— 堆栈是从「异常抛出点」往外一层层展开的,先看**第一行**
   (哪个文件哪一行),再看倒数第二行(谁调用的);
4. **二分法定位** —— 把可疑的配置/代码块注释掉再启动,看问题还在不在。
   这个项目的「桌宠拖垮预设」就是这么锁定的:注释掉桌宠那段,恋爱向立刻能挂;
5. **写临时脚本,别用 node -e** —— 引号转义会把你逼疯;写个 tmp-xxx.mjs 跑完删掉;
6. **去源头找证据,而不是猜** —— 这个项目最重要的一次排查,是解压 DSH 的会话日志
   (session.jsonl.zstd,用 Node 的 zlib.zstdDecompressSync 就能解),
   一条条看事件,最后发现「用户消息没有 source 字段」。日志不会骗人,猜测会。

## 8.4 报错处理:三条原则

**原则一:边界处一律兜住。**

    try { out = await dispatch(endpoint, payload) }
    catch (error) { out = { ok: false, error: { code: 'handler-error', message: String(error) } } }

HTTP 路由、事件钩子、定时任务 —— 这些地方往外抛异常,受害的是用户那一轮对话。

**原则二:兜住的同时把真实原因记下来。**

    } catch (e) {
      console.error('[roleplay] agent/pre-step failed:', e && e.stack ? e.stack : e)
      ...

不记堆栈的 catch,是给自己挖坑:以后只看到「操作失败」,永远查不出为什么。

**原则三:给调用方一个「形状正确」的兜底值。**

这一条是最反直觉的:catch 之后如果你 return undefined,调用方一读属性就崩,
而且报错信息完全指向别处(这个项目就因此绕了很久)。
正确做法是返回一个**结构合法的空值**:{ kind: 'enter', messages: [] } 之类。

【C++ 老习惯会坑你】C++ 里你可能习惯「让异常往上飞,顶层统一处理」。
在插件体系里这是行不通的:你的异常会变成用户界面上一个红牌,
而错误信息往往丢失了上下文。

## 8.5 编码:一个字符没对上,整个脚本报废(真事)

Windows 上有个历史遗留:PowerShell 5.1 读脚本时,如果文件开头没有 UTF-8 BOM,
它会**按系统 ANSI 编码解码**。于是:

- 文件里是 UTF-8 的中文 → 被当 ANSI 解释 → 变成乱码 → 脚本语法错误;
- 更阴的是用 PowerShell 的 Get-Content/Set-Content 去改文件:读的时候按 ANSI 解、
  写回去还是 ANSI,一进一出,文件彻底坏了(中文块全废)。

这个项目因此立了两条纪律,并且写进了测试门禁(T0b):

1. **pet/*.ps1 必须自带 UTF-8 BOM**(开头三字节 EF BB BF),否则测试直接红灯;
2. **改文件别用 PowerShell 的文本 cmdlet**;要批量改就写 Node 脚本,或者用编辑器/专门的工具。

顺手记一个更广的教训:**文件编码是可以被代码破坏的资产**。
你写工具链时,凡是「读文件—改—写回」的环节,都要明确编码(utf8)、明确换行符(LF/CRLF),
并且对中文这种多字节内容特别小心。

## 8.6 数据安全:用户的存档不是你的实验田

这个项目碰的是用户的角色数据(角色卡、记忆、亲密度、日记)。
所以有几条硬规矩:

1. **改动任何数据相关目录之前先做快照**(项目里用 robocopy 复制到 roleplay-persist 下);
2. **绝不删除/移动/覆盖用户数据目录**,除非用户明确要求;
3. **写盘前先备份**:主存档写之前先存一份 .bak(这份备份曾经因为路径 bug 从来没生效过,
   修好之后才算真的安全);
4. **分层备份**:写前 .bak(L1)→ 每日快照(L2)→ 跨工作区镜像(L3)→ 缺文件时回流(L4);
5. **读盘要容错**:JSON 解析失败不能让整个插件挂掉,要给默认值(fresh 状态)继续跑。

    try { const p = JSON.parse(await fs.readText(await resolveFile(...))) }
    catch (e) { /* fresh —— 就当这个角色还没有进度 */ }

## 8.7 版本与发布:两条容易忘的链路

**第一条:版本号必须同步改两处。** lib/index.js 里有个常量:

    const PKG_VERSION = '1.5.17'

它要和 package.json 的 version 一致。为什么?因为这个插件有个「物化」机制:
启动时把包内的预设文件复制到用户的 .agent-presets 目录,并写一个版本标记
(.rp-version)。标记和当前版本一致就跳过复制。**如果你改了预设文件却忘了升版本号,
物化器会认为「没变化」,用户加载的还是旧代码** —— 这个坑项目真踩过,表现为
「改了半天没效果」。

**第二条:缓存版本号。** 预设里那些 import './lib/chat-core.mjs?v=2',
那个 v 是给模块缓存用的版本号;改了被导入的文件,最好把它 +1,
否则可能还是旧缓存(尤其在被长期缓存的运行环境里)。

发布流程(这个项目的实际做法):

    node test/core.test.mjs                     # 1. 全绿
    # 2. 同步镜像目录、备份快照
    dsh plugin --profile web remove @ajuwm/dsh-roleplay-plugin
    dsh plugin --profile web add file:D:/dsh/repo/dsh-roleplay-plugin   # 3. 刷新运行副本
    # 4. 让用户重启 DSH 验收

**小步提交**也是纪律:一个 bug 一次提交,提交信息写清「现象 → 根因 → 修法」,
以后回看能救命。
